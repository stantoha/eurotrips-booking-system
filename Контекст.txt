EUROTRIPS BOOKING SYSTEM — Повний контекст для Claude Code
1. КОМПАНІЯ ТА ПРОДУКТ
Eurotrips (eurotrips.ua) — український туроператор. Продає автобусні та авіатури по Європі та світу через прямі продажі та агентську мережу. Система будується на заміну 1С-системі бронювання. Zoho CRM залишається — менеджери продовжують в ній працювати.
Що зберігається:
* Сайт eurotrips.ua — не чіпаємо, система інтегрується з ним
* Zoho CRM — двостороння синхронізація через webhook
* Існуюча агентська мережа — сотні агентів з різними комісіями
Мова системи: Тільки українська. Весь UI, повідомлення, назви турів, коментарі в коді.

7. ФІНАНСОВА МОДЕЛЬ
Каскад ціноутворення:
Собівартість (СВ) = Розміщення + Транспорт + Персонал + Гіди + ДОПи в СВ + Непрямі
Базова ціна = СВ + Маржа оператора
Ціна клієнта (gross) = Базова ціна + Доплати − Знижки
Агентська комісія = gross_price × commissionPct (10–30%)
Маржа оператора (net) = gross − СВ − AG_commission − Роялті − Непрямі
ДОПи (додаткові послуги):
* Продаються під час туру, не входять в базову ціну
* Комісія агента на ДОПи НЕ нараховується
* Мають власний P&L: СВ_ДОП = Гід + км + прямі витрати
Агентська комісія по CSV-даних (406 турів):
* Діапазон: 10% — 30%
* Budapest+Vienna: 30% комісія при 14.5% маржі = ризик негативного P&L
* Комісія диференційована по продукту, не однакова для всіх

8. АРХІТЕКТУРНІ РІШЕННЯ (ADR)
ADR-003: Departure Entity — Варіант A прийнятий
Проблема: стара 1С система має Tour → Departure → Booking. Нова схема: Tour → Booking (Tour містить дату виїзду).
Рішення (ПРИЙНЯТО для MVP): Tour = Departure. Кожен виїзд = окремий Tour запис.
* Код туру кодує продукт+дату: LP26010301 = Лапландія 2026-01-03
* Поле product_code = групування виїздів одного продукту (LP, PN тощо)
* @@index([product_code, departure_date]) для запитів "всі дати Лапландії"
Реліз 2: Departure як окрема сутність (еволюційно, без breaking changes)
Реліз 3: Повноцінна міграція Tour+Departure

19. UX/CJM РІШЕННЯ (з wireframe документу)
Два ключових сценарії задокументовані:
Сценарій A — Агент бронює тур (7 кроків):
1. Логін → автовизначення типу агента (standard/network)
2. Пошук → показати нетто-ціну одразу + розбивка комісії

4. Дані клієнта → збережені клієнти агента (вибір зі списку)
5. Підтвердження → Summary сторінка перед відправкою
6. Статус → email/Telegram при кожній зміні статусу
7. Документи → share-link + можливість брендингу агентства
Сценарій B — Менеджер веде лід до оплати (7 кроків):
1. Лід → єдина черга з маркером джерела
2. Призначення → round-robin + override
3. Консультація → CRM нотатки + задачі
4. Бронювання → швидка форма з pre-fill з ліда
5. Рахунок → автогенерація PDF
6. Передоплата → LiqPay посилання в один клік
7. Підтвердження → автоматичний email клієнту

23. ВАЖЛИВІ ТЕХНІЧНІ ДЕТАЛІ
Числа в API: Prisma Decimal повертає {s,e,d} об'єкт. Є case-transform хук який ламав Decimal — виправлено. Завжди перевіряй що total_amount, deposit_paid etc приходять як числа, не як об'єкти.
snake_case vs camelCase: Backend повертає snake_case (PostgreSQL конвенція). Frontend перетворює через хук. JWT payload — snake_case (agent_code, full_name).
Booking number: Генерується автоматично в src/shared/utils/booking-number.ts. Формат ET-YYYY-NNNNN. НІКОЛИ не приймати від клієнта.
Amounts: Всі суми в EUR. Відображення: toLocaleString('uk-UA', {style:'currency', currency:'EUR'}).
liqPayRoutes і zohoWebhookRoutes: Свідомо закоментовані через відомі баги. Не розкоментовувати без окремого дослідження і фіксу.
nixpacks.toml: nixPkgs: ["nodejs_20", "openssl"]. nodejs_20 включає npm. openssl потрібен для Prisma. НЕ видаляти openssl.
Vercel: Root Directory = frontend/. vercel.json вже там. SPA rewrite /(.*) → /index.html.
Railway: Root Directory = порожній (backend IS root). startCommand: node dist/src/main.js. Builder: NIXPACKS.
