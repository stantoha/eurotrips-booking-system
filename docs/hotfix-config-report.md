## Причина аварії — механізм

Гейт `ZOHO_ENABLED` був доданий правильно і працював. Ламалось раніше.

Railway (як і Docker Compose та GitHub Actions) зберігає незадану змінну як
**порожній рядок**, а не `undefined`. Для Zod це дві різні речі:

```
.optional()  спрацьовує лише на undefined
.default()   спрацьовує лише на undefined
""           -> це ЗАДАНЕ значення, валідація йде далі
```

Тому `ZOHO_CLIENT_ID=""` проходив `.optional()`, доходив до `.min(1)` і падав.
`superRefine` виконується **після** розбору полів, тож до гейта справа не
доходила взагалі.

> **Уточнення до діагнозу з тікета.** У тікеті п.1 — «зробити всі `ZOHO_*` поля
> `.optional()` у базовій схемі». Вони **вже були** `.optional()`:
> `z.string().min(1).optional()`. Проблема була не у відсутності `.optional()`,
> а в тому, що `.min()` виконується для будь-якого заданого значення, а `""`
> для Zod задане. Тому одного `.optional()` було б недостатньо — саме
> нормалізація порожнього рядка є ключовою правкою.

## Знайдено понад тікет: 8 мін того самого класу

Нормалізація полагодила не лише `ZOHO_*`. Без неї на `""` падали або тихо
ламались:

| Змінна | Що ставалось на `""` |
|---|---|
| `APP_URL`, `FRONTEND_URL` | `.url()` на порожньому рядку → падіння старту |
| `EMAIL_FROM` | `.email()` → падіння старту |
| `LOG_LEVEL` | `z.enum()` → падіння старту |
| `ZOHO_BASE_URL`, `ZOHO_AUTH_URL` | `.url()` → падіння старту |
| `APP_PORT` | `z.coerce.number()` дає **0** — порт нуль |
| `BCRYPT_ROUNDS` | `z.coerce.number()` дає **0** — хешування пароля в нуль раундів |

Два останні — не падіння, а тиха деградація, і `BCRYPT_ROUNDS=0` це діра в
безпеці: пароль фактично не хешується. Ці міни існували ще до етапу 1 і не
спрацювали лише тому, що ніхто не задавав ці змінні порожніми.

## Ширше правило: результат перевірки

Тікет просив перевірити `BREVO_API_KEY`, `TURBOSMS_API_KEY`, `REDIS_URL`.

| Змінна | Стан | Ризик падіння старту |
|---|---|---|
| `REDIS_URL` | у схемі, `.optional()` | немає; тепер переживає й `""` |
| `BREVO_API_KEY` | **у схемі відсутня** | немає |
| `TURBOSMS_API_KEY` | **не згадується ніде в `src/`** | немає |

`BREVO_*` читається напряму: `process.env.BREVO_API_KEY ?? ''`, далі guard
`if (!BREVO_API_KEY) { warn; skip; }`. Це вже правильний захисний патерн —
впасти не може. Сам `email.service.ts` до того ж виключений з
`tsconfig.build.json`.

## Деплой: білд падав із іншої причини

Тікет просив перевірити стан деплою після мержу й не вірити «зеленому мержу».
Перевірка через Railway API дала несподіване.

**Останній деплой `f652eab7` — `FAILED`.** Але впав він **не** на валідації
конфігу. Білд-лог:

```
[stage-0  9/11] RUN npm run build && npx prisma migrate deploy
  npm run build              -> tsc пройшов успішно
  npx prisma migrate deploy  -> Error: P1012
                                Environment variable not found: DATABASE_URL
Build Failed: exit code 1
```

`prisma migrate deploy` стояв у `build.buildCommand`, а у build-фазі Nixpacks
немає змінних оточення сервісу — вони інжектяться в рантаймі. Тобто міграція
там не могла працювати **в принципі**, і її збій валив увесь білд ще до того,
як застосунок стартував.

Перенесено в `deploy.preDeployCommand` (коміт `5b43764`) — цей крок виконується
з рантайм-змінними, перед запуском нових контейнерів. Поведінка «міграції
накочуються автоматично» зберігається.

> ⚠️ **Не перевірено на живому Railway.** Якщо інфраструктуру зручніше правити
> окремо — коміт `5b43764` можна викинути з гілки, конфіг-фікс від нього не
> залежить. Але без цієї правки хотфікс до прода не доїде.

## Розбіжності з завданням

**1. `ZOHO_*` уже були `.optional()`.** Пункт 1 тікета виходив із того, що вони
обовʼязкові в базовій схемі. Насправді `z.string().min(1).optional()` — тобто
`.optional()` був, а падало на `.min()` через порожній рядок. Виконав і п.1,
і п.3, але ключовим виявився саме п.3.

**2. `BREVO_API_KEY` / `TURBOSMS_API_KEY` у схемі відсутні.** Тікет припускав,
що вони можуть бути обовʼязковими в базовій схемі. Їх там немає взагалі:
BREVO читається повз схему з guard'ом, TURBOSMS не згадується ніде.

**3. Довжину токена теж винесено під гейт.** Тікет цього не просив: п.1 казав
лишити «формат, якщо значення задане». Але `.min(16)` для `ZOHO_WEBHOOK_TOKEN`
означав би, що залишкове коротке значення кладе застосунок із **вимкненою**
інтеграцією — той самий клас аварії. Тому перенесено в `superRefine`. Якщо це
розходиться з задумом — легко повернути.

**4. Деплой падав не з тієї причини, яку описує тікет.** Тікет виходив із того,
що контейнер стартує й помирає на валідації. Це справді сталось (лог аварії
в тікеті — рантаймовий), але **останній** деплой упав раніше, на build-фазі,
через `DATABASE_URL`. Тобто причин було дві, і друга лишалась невидимою.

**5. Deploy-логи аварії вже недоступні** — Railway їх не віддає
(`deploy: []`). Відновлював картину з build-логів і тексту помилки з тікета.

## Ризики

**1. Перший деплой після мержу.** Він або вперше за два місяці стане `SUCCESS`,
або покаже наступну проблему — тепер уже в `preDeployCommand`. Статус треба
подивитись явно: `CRASHED`/`FAILED` у списку Railway виглядає майже як
`SUCCESS`.

**2. Історія деплоїв.** Усі деплої з реальним білдом, починаючи з 12 липня,
мають статус `FAILED`. При цьому прод обслуговує актуальний код (перевірено:
ендпоінт від 25.08 працює). Що саме означає цей статус у їхньому пайплайні —
не зʼясовано, але «зелений мерж» тут не свідчить ні про що, і це варто
розібрати до етапу 2.

**3. `BCRYPT_ROUNDS=0`** був досяжний через порожню змінну. Зараз закрито, але
варто перевірити, чи немає в базі користувачів, створених у такому стані.

**4. Клас проблеми ширший за конфіг.** Порожній рядок ≠ `undefined` — це
стосується будь-якого читання `process.env` у проєкті, не лише Zod-схеми.
7 змінних повз схему працюють із `?? ''`, що для них безпечно, але патерн
варто уніфікувати.
