C-03 · Login завжди редіректить на /dashboard — ігнорує state.from
UX · Redirect після логіну · App.tsx:33 + ProtectedRoute.tsx:82–86 · UX
▼
ПРОБЛЕМА

ProtectedRoute зберігає шлях що запитував користувач перед редіректом на логін: state={{ from: location.pathname }}. Але LoginPage та LoginForm ігнорують цей state і завжди відправляють на /dashboard. Менеджер, якому надіслали посилання на конкретне бронювання /bookings/1247, після логіну потрапляє на дашборд — і губить контекст.

🟡 Сценарій: Операційник отримує посилання на картку туру, натискає — бачить логін. Логіниться — і опиняється на дашборді. Мусить знову шукати потрібну сторінку.
ПОТОЧНИЙ КОД
// ❌ App.tsx:33 — завжди /dashboard, ігнорує state.from
<LoginForm onSuccess={() => window.location.replace('/dashboard')} />

// ❌ Додатковий antipattern — window.location замість React Router navigate
ВИПРАВЛЕННЯ
// ✅ LoginPage — зчитуємо state.from через useLocation
const LoginPage: React.FC = () => {
  const { isAuthenticated } = useAuth();
  const location = useLocation();
  const navigate = useNavigate();
  
  // state.from прокидує ProtectedRoute
  const from = (location.state as { from?: string })?.from ?? '/dashboard';
  
  if (isAuthenticated) return <Navigate to={from} replace />;
  
  return (
    <LoginForm onSuccess={() => navigate(from, { replace: true })} />
  );
};

C-04 · require() у ESM-модулі api.ts — Vite antipattern
Architecture · Circular dependencies · api.ts:134 · ARCH SEC
▼
ПРОБЛЕМА

В api.ts:134 є динамічний require() для отримання authStore — це CommonJS синтаксис у ESM-модулі. Vite попереджатиме під час build. Крім того, window.location.href = '/login' у refresh interceptor (рядок 113) замінить всю React-аплікацію і скине весь стан — замість акуратного logout через React Router.

ПРОБЛЕМНИЙ КОД
// ❌ api.ts:134 — CommonJS require() у ESM
const { useAuthStore } = require('../store/authStore') as {...};

// ❌ api.ts:113 — повне перезавантаження замість React Router
window.location.href = '/login';
РЕКОМЕНДОВАНЕ ВИПРАВЛЕННЯ
// ✅ Варіант 1: useAuthStore.getState() напряму (якщо немає circular dep)
import { useAuthStore } from '../store/authStore';

function getAuthActions() {
  const state = useAuthStore.getState();
  return { getAccessToken: () => state.accessToken, ... };
}

// ✅ Варіант 2: зовнішній navigateFn — ін'єкція через setNavigator()
let navigateFn: ((path: string) => void) | null = null;
export const setNavigator = (fn: typeof navigateFn) => { navigateFn = fn; };

// У App.tsx: api.setNavigator((path) => navigate(path));

// ✅ Замість window.location.href:
navigateFn?.('/login') ?? (window.location.replace('/login'));
Коментар: Варіант 1 простіший. Zustand дозволяє getState() поза компонентами — це офіційний паттерн для Zustand v4+. Circular dep вирішується через реєстрацію в окремому store-registry.ts.

M-05 · Magic string 'network' в useAuth — не через AGENT_TYPE_CONFIG
Consistency · useAuth.ts:129 · CONS
▼
ПРОБЛЕМА

Перевірка типу агента: user?.agent_type === 'network' — magic string. Якщо назва типу зміниться, або переміниться на enum — треба шукати по всьому коду. Треба використовувати той самий AgentType тип.

ВИПРАВЛЕННЯ
// ✅ Використовуємо AgentType константу
const NETWORK_AGENT_TYPE: AgentType = 'network';
const isNetworkAgent = isAgent && user?.agent_type === NETWORK_AGENT_TYPE;

// Або ще краще — через хелпер:
const isNetworkAgent = isAgent && hasAgentType('network');
✅ ЩО ДОБРЕ12 правильних рішень
// Фіксуємо що вже зроблено правильно — зберігаємо ці підходи
🔐 Безпека токенів — in-memory + HttpOnly Cookie
authStore.ts: access token зберігається тільки в пам'яті (Zustand), refresh token — HttpOnly Cookie. Не використовується localStorage. Це правильна реалізація ADR-001 §3.1 — захищає від XSS-атак на токени.
⚡ Queue pattern для concurrent refresh
api.ts: Коли кілька запитів отримують 401 одночасно — тільки один refresh-запит відправляється, решта очікують у pendingQueue. Це запобігає race condition і множинним refresh-запитам.
♿ Accessibility у LoginForm
Всі інтерактивні елементи мають aria-label, aria-invalid, aria-describedby, role="alert" для помилок, aria-hidden на декоративних іконках, aria-busy на кнопці. Зразковий рівень a11y для форми входу.
🎯 Config-driven statuses pattern
statuses.ts: всі статуси описуються через єдиний конфіг-об'єкт з label/icon/colorVariant/description. Компоненти не hard-code кольори — читають з конфігу. Легко масштабується на нові статуси.
🏷️ isPulsing для активних статусів
Ідея з isPulsing: true для статусів "нова заявка", "у поїздці", "overdue" — відмінне UX-рішення. Дає системі візуальне сигналювання без зайвого коду в компонентах.
📝 Zod-валідація форми входу
Схема з mode: 'onTouched' — помилки показуються після blur, не при введенні. Правильний UX для форм. Zod-схема чітко відділена від компоненту.
🔄 Lazy loading для всіх сторінок
App.tsx: всі pages завантажуються через React.lazy() — початковий бандл мінімальний. Менеджер завантажує тільки свої сторінки, агент — свої.
🔑 RBAC helpers у useAuth
Зручні boolean helpers: isAdmin, isManager, canSeeMargin, canSeeAllAgents, isNetworkAgent — компоненти не пишуть user.role === 'manager' напряму. Централізована RBAC логіка.
🛡️ state.from у ProtectedRoute
Збереження поточного URL перед redirect на логін через state={{ from: location.pathname }} — правильний паттерн. (Але: LoginPage його не читає — C-03 вище.)
🧪 DEV-only тестові акаунти у LoginForm
Блок тестових акаунтів захищений через import.meta.env.DEV — не потрапить у production build. Зручно для розробки і QA, не несе ризиків у проді.
📦 Zustand selectors для re-render оптимізації
authStore.ts: окремо експортовані selectors selectUser, selectIsAuthenticated тощо. Компоненти підписуються тільки на потрібний шматок стору — мінімум зайвих re-renders.
👁️ Show/hide password у LoginForm
Кнопка toggle пароля з tabIndex={-1} — не ламає Tab-навігацію. aria-label правильно описує дію в обох станах.
