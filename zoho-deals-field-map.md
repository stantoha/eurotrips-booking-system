## Стадії угоди (layout «Поїздки», pipeline `Поездка`)

Перевірено емпірично через `GET /crm/v8/Deals?fields=Stage,Pipeline`:
**API повертає й приймає display-значення**, не `actual_value`.

```json
"Stage": "5. 100 проц."
"Stage": "3. Ожидание оплаты"
"Pipeline": "Поездка"
```

Запис підтверджено непрямо: продакшн-Deluge виконує
`zoho.crm.updateRecord("Deals", potID, {"Stage":"4. Бронь"})` тисячі разів на
добу і працює. Якби API вимагав `actual_value`, ці функції падали б.

| Видно менеджеру | Передавати в API |
| :---- | :---- |
| 1. Новая | `1. Новая` |
| 2. Переговоры | `2. Переговоры` |
| 3. Ожидание оплаты | `3. Ожидание оплаты` |
| 4. Бронь | `4. Бронь` |
| 5. 100 проц. | `5. 100 проц.` |
| 6. Завершена успешно | `6. Завершена успешно` |
| 7. Отказ | `7. Отказ` |
| 8. Отказ в выдаче визы | `8. Отказ в выдаче визы` |

Обовʼязкові при створенні: `Deal_Name`, `Stage`, `Pipeline` (= `Поездка`).

Реалізація — `src/shared/utils/zoho-stage-map.ts`.
Актуальне джерело правди — «Контракт синхронізації ETOS ↔ Zoho CRM» v3, розділ 5.

## Ключі прив’язки

- `Deal_ID_Ekanikuly` (bigint) — **єдине unique-поле**, слід попередньої міграції. Прецедент для `ETOS_Booking_ID`.  
- `field134 «Номер заявки»` — autonumber (з 102974). Через API **тільки читання**, для запису непридатне.  
- `field6 «Поїздка»` — lookup у модуль `Travel` (тури).  
- `field25` — lookup на батьківську угоду (Deals→Deals).

## Модулі

Усього 84, кастомних 9: `Travel`, `Agencies`, `Requisites`, `Promocodes`, `Customer_Survey`, `PreInvoces`, `CustomModule3`, `CustomModule4`, `Achievement_Rules`. `DealHistory` — read-only трекер змін полів, придатний для conflict resolution. Решта — системні модулі Zoho Voice of Customer (`Voc*`), порожні.
